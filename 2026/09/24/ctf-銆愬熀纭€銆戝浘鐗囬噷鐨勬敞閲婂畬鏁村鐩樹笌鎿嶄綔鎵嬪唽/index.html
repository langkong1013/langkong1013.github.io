【基础】图片里的注释

langkong10132026-09-242026-10-28

零基础详解版 —— 每条命令都讲清「作用 · 原理 · 为什么这么做」

平台：ctf.bi6pcr.com | 题目：图片里的注释（90 分 · 取证/基础）

一、题目回顾

题目描述：下载这张 PNG。图片本身只是一个小色块，文件里另有一段文本注释。

用记事本打开，搜索 flag{ ；或者 strings photo.png

题目提示：注释写在 PNG 的 tEXt 块里，关键字是 Comment。

一句话思路：

PNG 文件除了存图像，还能附带一段“文本注释”，存在一种叫 tEXt 的数据块里。
这段注释不影响看图（看图软件只读图像数据、忽略注释），但用文本方式打开就能看到它。
所以：用 strings 把里面的可打印字符串抽出来（或记事本搜索 flag{）→ 得到注释里的 flag。

结果：注释文本中的 flag{…} 就是答案。

说明：本题的 flag 存放在题目提供的 photo.png 的 tEXt 注释里，需读取该文件获得；本手册把方法与原理讲透，具体 flag 字符串请以你实际读出的内容为准。

二、知识点详解

2.1 PNG 文件是怎么“装东西”的：块（chunk）结构

PNG 不是一整块连续像素，而是由若干“数据块（chunk）”拼起来的。

文件最前面固定有 8 个字节的“签名”，用来表明“我是 PNG”：

89 50 4E 47 0D 0A 1A 0A

签名之后，就是一串接一串的块。每个块的排列固定为四部分：

部分 长度 说明
长度 Length 4 字节 指明后面“数据”部分有多少字节（大端字节序）
类型 Type 4 字节 4 个 ASCII 字母，标明这是什么块，如 IHDR / tEXt / IDAT / IEND
数据 Data Length 字节 这个块真正装的内容
校验 CRC 4 字节 用来校验数据有没有损坏

把一块“读”完，就按 长度+8+4 跳到下一块，直到文件结束。

2.2 关键块类型（记住这几个就够用）

块类型 作用
IHDR 图像头：宽、高、位深、颜色类型等（看图软件靠它渲染）
PLTE 调色板（有些格式用）
IDAT 真正的图像像素数据（可能有多块）
IEND 文件结束标记
tEXt 文本注释（Latin-1 编码），格式为：关键字 + 0x00 + 文本 ← 本题 flag 就在这里
zTXt 压缩后的文本注释
iTXt 国际化文本注释（UTF-8）

本题的关键字是 Comment，也就是注释里“Comment\0后面那段文字”才是内容。

2.3 为什么注释不影响看图

看图软件渲染图像时只读 IHDR 和 IDAT，直接跳过 tEXt 等辅助块。所以图片显示正常，注释却“隐身”在文件里——这正是取证题爱用的藏信息手法。

2.4 strings 命令的原理

strings 做的事：把文件从头到尾扫一遍，找出所有“连续的可打印字符”（默认长度 ≥ 4），逐行打印出来。它不管文件是不是文本，所以能从二进制图片里“捞”出注释文字。

因为图片的像素数据大多是乱码（不可打印），而注释是正常英文/可打印字符，所以 flag 那段会干净地出现在 strings 的输出里。

2.5 手算演示：自己写脚本拆出 tEXt 注释

不借助任何工具，用 Python 按上面的“块结构”规则，也能把注释读出来：

import struct
data = open(‘photo.png’, ‘rb’).read()
assert data[:8] == b’\x89PNG\r\n\x1a\n’ # 1) 先验证 8 字节签名
i = 8 # 2) 从签名之后开始
while i < len(data):
length = struct.unpack(‘>I’, data[i:i+4])[0] # 3) 读 4 字节“长度”(大端)
ctype = data[i+4:i+8].decode(‘ascii’) # 4) 读 4 字节“类型”
chunk = data[i+8:i+8+length] # 5) 读 length 字节“数据”
if ctype == ‘tEXt’: # 6) 是文本注释就打印
print(chunk.decode(‘latin-1’))
i += 8 + length + 4 # 7) 跳到下一个块(长+类型+数据+CRC)

逐行解释：

  • ① data[:8] 取出前 8 字节，与 PNG 固定签名比对，确认文件格式。
  • ② i=8：跳过签名，从第一个块的“长度”字段开始。
  • ③ 前 4 字节是大端无符号整数，就是数据长度（>I 中的 > 表示大端、I 表示 4 字节无符号）。
  • ④ 紧接 4 字节是块类型，解成 ASCII 字符串。
  • ⑤ 再往后 length 字节就是块的数据内容。
  • ⑥ 若类型是 tEXt，把数据按 latin-1 解出来，就是 “Comment\0注释文字”。
  • ⑦ 一个块 = 4(长)+4(类型)+length(数据)+4(CRC)，所以下一块从 i+8+length+4 开始。

三、完整操作步骤（Step by Step）

Step 0 拿到文件

在题目页点下载，保存 photo.png 到本地。

Step 1 方法 A —— 用 strings 直接捞（推荐，最快）

strings photo.png | grep -i flag

作用：抽出所有可打印字符串，再筛出含 flag 的行。

原理：strings 扫全文件收集可打印字符；grep 过滤只留含 flag 的行。

也可以先不加 grep，整体看一眼：

strings photo.png

通常在输出里能看到类似这样一行：

Commentflag{………………..}

（前面的 Comment 就是注释的关键字，紧跟其后即内容。）

Step 2 方法 B —— 用 exiftool 看元数据（更直观）

exiftool photo.png

作用：显示图片的元数据，其中会有一行 Comment : flag{…}。

原理：exiftool 专门解析各类文件的元数据字段，PNG 的 tEXt 就是其中一种。

没装的话：sudo apt install libimage-exiftool-perl

Step 3 方法 C —— 记事本打开搜索（Windows 零工具）

  • 右键 photo.png → 打开方式 → 记事本（或用记事本“文件→打开”选中它）。
  • 会看到一堆乱码，按 Ctrl+F 搜索 flag{ 。
  • 找到后，把 flag{…} 完整复制出来即可。

原理：记事本把文件按文本读，注释是明文，所以能被搜到；像素乱码不影响搜索。

Step 4 方法 D —— 用上面的 Python 脚本精确提取

把 2.5 节的脚本存成 png_comment.py 运行：python3 png_comment.py，输出即为 Comment 注释全文。适合需要“只取注释、不掺乱码”的场景。

四、易错点与报错处理

现象 / 报错 原因 怎么办
strings 输出里没看到 flag 字符串被压缩过（zTXt/iTXt） 改用 exiftool，或用 Python/PNG 解析库读出 tEXt/zTXt/iTXt
strings: command not found 没装 binutils 里的 strings sudo apt install binutils；或直接用 exiftool / 记事本
记事本里搜不到 flag{ 字被换行/分隔，或看的是别的块 搜 “flag” 而不带 “{”；或用 strings 查看
grep 大小写没匹配到 flag 可能大小写不一 用 grep -i flag 忽略大小写
exiftool 无输出 Comment 该注释不在 tEXt 而在 zTXt 用 Python 遍历块，或在线 PNG chunk 查看器
flag 抄错字符 截图/肉眼易混 0/O、l/1 直接从 strings 输出复制，不要手打

五、速查卡

一句话记法：strings 捞注释 → 找到 Comment 后的 flag。

strings photo.png | grep -i flag # 抽出并筛选出 flag
strings photo.png # 直接看全部可打印字符
exiftool photo.png # 看元数据里的 Comment
python3 png_comment.py # 精确提取 tEXt 注释（脚本见 2.5）

PNG 结构速记：8 字节签名 + 若干块；每块 = 长度(4) + 类型(4) + 数据 + CRC(4)；注释在 tEXt 块，格式 关键字\0文本。

附录：思路迁移（同类题的通用套路）

藏信息的位置 特征 读取方法
PNG tEXt / zTXt / iTXt 注释（本题） strings 能看到 Comment/flag strings / exiftool / 遍历块
PNG 尾部附加数据 图像数据结束后还有明文 strings / tail -c / 记事本拉到最底
JPEG EXIF 注释 图片信息里带 Comment/UserComment exiftool / exiv2
文件本身是压缩包（伪装图片题） 文件头是 PK file 确认 → unzip/7z
图片里嵌了别的文件 binwalk 能扫出多个签名 binwalk -e / foremost 提取

主线记法：拿到可疑文件，先 file 看真身，再 strings 捞明文，再按类型深挖。
